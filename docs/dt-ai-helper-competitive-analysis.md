## 1. 结论摘要

这个程序确实是一套以 RPA 为执行层、以 AI 为内容与决策层的私域和短视频运营工具。用户最初的判断基本正确：它能登录或复用已经登录的社交平台账号，自动操作微信、抖音、小红书、快手、视频号等平台，完成内容发布、曝光获客、私信处理、好友运营和朋友圈营销。

它不是单纯的“网页套壳”，而是一个混合式 Windows 桌面程序：

- Electron + React 提供完整桌面界面；
- Node.js 侧使用 Playwright、Midscene、nut.js 等能力自动操作浏览器；
- 内置 Python 程序通过 Windows UI 自动化、截图、OCR 等方式控制 PC 微信；
- 视频素材上传阿里云 OSS，使用阿里云 Timeline Web SDK 预览，并通过服务端云任务完成剪辑合成；
- 本机 HTTP、WebSocket 用于 Electron 与 Python 进程通信；
- 云端服务负责账号授权、AI 能力、配置下发、任务协同和部分平台接口；
- 本地数据库保存部分账号、任务和运行状态；
- 程序具备自动更新能力。

不同平台的实现并不完全相同：

- PC 微信：主要是本地窗口控制、鼠标键盘模拟和 OCR 识别，属于典型桌面 RPA；
- 抖音、小红书、快手、视频号的内容发布与曝光：主要是浏览器自动化，复用 Cookie 或登录状态；
- 抖音 AI 客服：从程序结构看，除了浏览器操作，还存在账号授权、云端接口和 WebSocket 协作，不能简单理解为全程模拟点击；
- AI：负责理解聊天内容、生成回复、辅助生成运营内容；
- 工作流：负责按条件和步骤把 AI、浏览器操作、桌面操作、等待、重试、审批串联起来。

对我们自己的产品，最终产品形态应明确为“完整桌面 App”，普通用户不需要在桌面客户端和网页控制台之间来回切换。云端后台仍然存在，但它是 App 背后的服务，不是要求用户额外打开的另一套操作界面。企业管理员将来可以有可选 Web 管理端，但员工日常运营应在一个 App 内闭环完成。

客户端技术选型确定为 Tauri，而不是 Electron。现有 Web 前端并非作废：Tauri 的界面本身就是由 WebView 承载 React 页面，所以现有 React、TypeScript、Ant Design、路由、状态管理和 API 代码可以继续复用。取消的是“浏览器网页作为普通用户主产品”的交付方式，不是删除已经完成的前端业务代码。

### 5.3 内容生产与分发

程序具备从素材到发布记录的完整链路：

1. 素材进入素材库；
2. 创建下载或剪辑任务；
3. 批量剪辑形成多个成品；
4. 选择抖音、小红书、快手、视频号等平台；
5. 选择账号、填写标题和话题；
6. 浏览器自动进入创作者后台并上传；
7. 点击发布并等待结果；
8. 保存发布记录，失败时记录错误。

运行日志中观察到了抖音真实发布成功链路：启动浏览器、进入发布页、上传视频、填写标题与话题、点击发布、确认成功、关闭浏览器。日志中也出现过创作者页面元素定位失败，说明该能力依赖网页结构，页面改版后需要持续维护选择器和识别策略。

视频“剪辑”和视频“发布”使用两套不同机制：剪辑主要通过阿里云云端任务完成，发布则由本地浏览器 RPA 操作各平台创作者后台。

### 5.4 视频剪辑专项结论

进一步检查安装包后可以确认，竞品的主要视频剪辑链路不是在用户电脑运行完整 FFmpeg，而是使用阿里云 OSS 和智能媒体服务 IMS/ICE 的云剪辑体系。

客户端侧已经证实的证据包括：

- 主页面直接加载 `https://g.alicdn.com/thor-server/video-editing-websdk/4.13.4/player.js`；
- 页面动态加载同版本 `player.css`；
- 代码调用 `window.AliyunTimelinePlayer`；
- 代码调用 `AliyunTimelinePlayer.parseTimeline` 解析剪辑时间线；
- 转场预览资源来自 `ice-pub-media.myalicdn.com`；
- 客户端通过 `/upload/token/sts` 获取临时凭据；
- 客户端内置阿里云 OSS SDK，并使用 STS 将视频、图片和音乐素材上传 OSS；
- 客户端向自己的服务端提交 `create_job`、`one_key_video` 和模板剪辑任务；
- 客户端通过 `get_job_status` 轮询任务状态；
- 成片通过下载任务接口获取，再进入多平台发布流程。

观察到的关键业务接口包括：

```text
/upload/token/sts
/video_creation/material_lib/upload
/video_creation/preview/create_job
/video_creation/preview/get_job_status
/video_creation/editing_task/one_key_video
/video_creation/editing_task/template-video/submit
/video/download/task/get_download
```

安装包中没有发现可供该产品直接执行剪辑的 `ffmpeg.exe`、`ffprobe.exe`、`ffmpeg-static` 或 `fluent-ffmpeg`。包内的 `opencv_videoio_ffmpeg4110_64.dll` 属于 OpenCV 的视频读写组件，可用于读取视频帧，但不能据此认定产品在本地完成成片渲染。

因此，客户端侧可以确认的流程是：

```text
选择本地素材
→ 获取 STS 临时凭据
→ 上传素材到阿里云 OSS
→ 生成 Timeline 配置
→ AliyunTimelinePlayer 在 App 内预览
→ 提交炼刀服务端剪辑任务
→ 轮询云端 Job 状态
→ 获取成片并下载或发布
```

安装包不包含炼刀服务端代码，所以无法直接看到其最终调用的阿里云 OpenAPI 名称。理论上服务端也可能把 Timeline 转换后用自建渲染集群处理；但结合阿里云 Web SDK、`AliyunTimelinePlayer`、ICE 公共素材域名、OSS、Timeline 数据和异步 Job 模式，后端使用阿里云 IMS/ICE 完成合成的可信度很高。

阿里云官方文档也说明，Web SDK 用于编辑和生成 Timeline，实际请求应先发送给业务服务端，再由服务端通过 AccessKey 调用阿里云 OpenAPI；合成任务可以通过 Job ID 查询状态。这与竞品实现高度一致：

- [阿里云视频剪辑 Web SDK 接入说明](https://help.aliyun.com/zh/ims/developer-reference/access-the-video-clip-web-sdk)
- [阿里云智能生产制作与任务查询](https://help.aliyun.com/zh/ims/getting-started/intelligent-production-production-quick-start)
- [阿里云 Timeline 配置说明](https://help.aliyun.com/zh/ims/developer-reference/timeline-configuration-description)

## 6. 技术架构分析

### 6.1 总体结构

```text
┌─────────────────────────────────────────────────────────────┐
```

这是一种典型的混合 RPA 架构：浏览器自动化放在 Node.js/Electron 一侧，Windows 微信自动化和 OCR 放在 Python 一侧，桌面 UI 统一承载用户操作。

## 7. RPA 在本产品中的含义

RPA 是 Robotic Process Automation，即机器人流程自动化。它不是实体机器人，而是一段代替人操作电脑的程序。

在这个产品里可以简单理解为：

- AI 负责“理解和生成”：判断消息意图、生成回复、生成标题和内容；
- RPA 负责“动手”：打开窗口、识别按钮、点击、输入、上传、发送；
- 工作流负责“组织”：规定先做什么、后做什么、失败怎么办、何时需要人工确认。

例如自动回复微信私信的完整流程是：发现未读消息 → 打开会话 → 识别聊天内容 → AI 生成候选回复 → 检查敏感词或审批规则 → 输入并发送 → 保存日志和结果。

RPA 的局限也很明确：

- 页面或桌面 UI 改版会导致定位失效；
- 验证码、滑块和风控通常需要人工接管；
- 窗口被遮挡、分辨率变化和系统锁屏会影响桌面自动化；
- 高频、重复、机械化行为可能导致平台封禁；
- AI 生成内容错误时，RPA 会把错误真正发送出去，因此需要策略和审批保护。

## 9. 安全、合规和稳定性判断

### 9.1 二进制可信度

外层安装包、Electron 主程序和内置 Python 主程序均未发现 Authenticode 签名。影响包括：

- Windows 无法可靠验证发布者身份；
- 用户无法确认文件下载后是否被替换；
- 安装时更容易触发系统或杀毒软件警告；
- 企业客户难以建立可信的软件供应链。

这不是“程序一定恶意”的证据，但属于不应忽略的高风险发布缺陷。

本次按 SHA-256 和 MD5 做过公开信息检索，没有找到能够可靠对应这个确切样本的安全报告或信誉记录。搜索不到不代表安全，也不代表恶意，只能说明没有可直接引用的公开样本结论。从已解包资源看，观察到的主要行为与其宣传的 RPA 产品能力相符，但静态分析不足以排除运行时下载、云端指令和更新链路中的其他行为。

### 9.2 本地权限风险

程序需要接触：

- 微信窗口和聊天内容；
- 鼠标、键盘和剪贴板；
- 浏览器登录状态和 Cookie；
- 本地视频、图片和其他素材；
- 社交平台账号与消息；
- 云端 AI 和任务接口；
- 自动更新下载源。

一旦程序、更新源或云端账号被攻击，影响会明显高于普通内容管理软件。此类客户端必须做代码签名、更新包签名校验、最小权限、凭据加密、权限提示、远程任务授权和紧急停止。

### 9.3 平台账号风险

自动评论、私信、批量发布、模拟用户操作和 stealth 规避检测，可能违反平台规则或触发风控。常见后果包括验证码、限流、功能冻结、账号封禁甚至企业主体受限。

正式产品至少需要：

- 每个平台独立的动作频率和每日上限；
- 随机等待不能作为唯一保护，核心是业务频控；
- 新账号冷启动和风险等级；
- 连续失败自动熔断；
- 验证码或风控出现时立即转人工；
- 敏感动作审批；
- 账号健康度和告警；
- 所有自动发送内容可追溯；
- 优先使用官方 API，RPA 只覆盖官方 API 不提供的部分。

### 9.4 隐私和数据合规

聊天内容、联系人、社交账号、素材和 AI 上下文都可能包含个人信息或商业秘密。产品设计必须明确：

- 哪些数据只在本地处理；
- 哪些内容会发往云端；
- 哪些内容会送给模型供应商；
- 每类数据保留多久；
- 用户如何查看、导出和删除；
- 企业管理员和普通员工各能看到什么；
- 日志、截图和失败现场是否自动脱敏。

### 9.5 账号与电脑绑定

目前从同事侧得到的信息是：该软件账号可能与电脑绑定，不是任何人拿到账号密码都能在任意电脑直接登录。由于本次没有账号，也没有实际运行程序，这一点尚未完成动态验证，不能把具体绑定机制写成已证实事实。

RPA 软件采用设备绑定是合理且常见的，通常同时出于三个目的：

- 按设备或席位收费，限制账号共享；
- 确保云端下发的任务只进入已授权电脑；
- 把平台 Cookie、微信登录态和本地执行环境固定在同一设备。

常见实现会组合使用账号、设备记录、本地安装标识和机器特征。机器特征可能来自 Windows 安装标识、硬件信息或客户端生成的密钥，但本样本究竟使用哪些字段还没有证据，不能直接推定。

对试用和采购的实际影响包括：

- 第一次登录可能自动占用一个设备席位；
- 更换电脑、重装系统或更换硬件后可能需要解绑；
- 如果先在临时虚拟机登录，正式 Windows 电脑可能无法继续使用；
- 同一账号可能只能同时运行一台或有限数量的设备；
- 账号密码、设备授权、平台账号 Cookie 可能是三套不同状态。

因此，在同事完成购买后，不要直接在临时虚拟机或个人主力机上首次激活。应先向销售确认设备数量、首次绑定规则、解绑入口、重装系统处理、换机次数和退款/试用政策，再选择一台专用 Windows 测试机完成激活。

我们自己的产品也需要设备授权，但不建议依赖不可解释的强硬硬件指纹。更稳妥的方案是：

1. App 首次启动生成设备 ID 和设备密钥对；
2. 私钥进入 Windows 安全凭据或 TPM 可用区域；
3. 用户登录后由云端为该设备签发授权；
4. 每个任务只能发送到明确授权的设备；
5. 管理员可以查看设备名称、最近在线时间和风险状态；
6. 用户可以自助解绑，企业可以配置设备数量和审批；
7. 重装、换机和硬件变更有清晰的恢复流程；
8. 不采集与授权无关的硬件和隐私信息。

## 10. 我们的产品形态：完整桌面 App

### 10.1 产品决策记录

原始计划是先提供 Web 版本。经过本次竞品和技术分析，产品主入口调整为 Tauri 桌面 App，原因是目标能力包含浏览器登录态管理、平台网页自动化、PC 微信窗口控制、OCR、鼠标键盘、后台常驻和本地文件处理，纯浏览器无法稳定获得这些系统权限。

这个调整不意味着把现有前端推倒重来：

- 保留 React 页面、组件、路由、状态管理、数据模型和 API 客户端；
- 用 Tauri WebView 直接承载这套前端；
- 通过统一 `PlatformAdapter` 增加文件、凭据、窗口、托盘、更新和本地 RPA 能力；
- 普通用户只安装和使用 App；
- Web 构建不再作为第一阶段的用户产品，可以保留给自动化测试、内部调试或未来企业管理端；
- 云端 FastAPI、LangGraph、知识库、权限和审计继续保留，App 只是统一入口和本地执行载体。

如果后续完全不提供公开 Web 入口，也仍然应维持 React 与 Tauri 原生能力之间的适配边界。这样可以让业务页面独立测试，避免页面到处直接调用 Rust 命令，未来做管理员 Web 端也不需要重写。

### 10.2 明确的用户体验原则

普通用户只使用一个桌面 App，所有日常操作在 App 内完成：

- 登录平台账号；
- 配置 AI 员工；
- 管理素材和知识；
- 创建工作流；
- 启停自动任务；
- 查看消息和私信；
- 查看发布、曝光和转化结果；
- 处理验证码、审批和人工接管；
- 查看错误、日志和账号健康度；
- 管理客户端更新。

云端服务对用户是透明的。App 可以通过 HTTPS、SSE 和 WebSocket 使用云端能力，但不能要求普通用户为了完成一个流程再打开网页后台。

可选的 Web 管理端只面向以下场景：

- 企业管理员管理组织、套餐、权限和设备；
- 负责人跨设备查看汇总数据；
- 运维人员查看全局服务健康状态；
- 客户端不在线时查看历史记录。

即使未来提供 Web 管理端，也应复用同一套 React 业务页面和平台 API，而不是维护两套产品。

### 10.3 推荐架构

结合当前 `agent-platform` 已确定的 React + Tauri 技术基线，推荐结构如下：

```text
┌──────────────────────── 完整 Tauri 桌面 App ────────────────────────┐
│ React 统一界面                                                       │
│ AI 员工 / 工作流 / 账号 / 素材 / 私信 / 发布 / 曝光 / 日志 / 人工接管 │
├──────────────────────────┬──────────────────────────────────────────┤
│ Tauri/Rust 原生宿主       │ 本地 RPA 执行器 Sidecar                  │
│ 窗口、托盘、更新、密钥库   │ Playwright + Windows UIA + OCR          │
│ 权限、进程和生命周期管理   │ 微信/浏览器/文件操作/截图/任务恢复        │
├──────────────────────────┴──────────────────────────────────────────┤
│ 本地加密状态 / 账号会话 / 执行队列 / 审计缓存 / 崩溃恢复              │
└──────────────────────────────┬──────────────────────────────────────┘
                               │ HTTPS / SSE / WebSocket（出站连接）
┌──────────────────────────────▼──────────────────────────────────────┐
│ agent-platform 云端                                                   │
│ 用户与企业 / AI 员工 / LangGraph / 视频云剪辑 / 知识 / 任务 / 审计     │
└─────────────────────────────────────────────────────────────────────┘
```

选择 Tauri 而不是照抄 Electron 的原因：

- 当前项目已经确定 Web 与 Tauri 共用 React 业务代码；
- 安装包和常驻内存通常可以比 Electron 更小；
- Rust 宿主更适合管理本机权限、进程、凭据和自动更新；
- Web 端仍可以复用相同页面，后续不必重写管理端；
- RPA 执行器可以作为受控 Sidecar，不需要把所有自动化能力都塞进 UI 进程。

需要注意：当前项目架构基线规定 Tauri 默认不内置 Python Agent 后端。完整本地 RPA 是一个明确的新需求，应增加“本地 RPA 执行器”边界，但不能把云端 FastAPI、LangGraph 或全部平台后端搬进桌面 App。需要扩展的是执行能力，不是复制一套后端。

### 10.4 App 内部模块

| 模块 | 用户看到的内容 | 核心职责 |
| --- | --- | --- |
| 首页 | 今日任务、消息、发布和异常 | 汇总运营状态和待办 |
| AI 员工 | 角色、目标、知识、语气和权限 | 配置数字员工 |
| 工作流 | 可视化步骤、触发条件、审批 | 编排 AI 与 RPA |
| 账号中心 | 微信、抖音、小红书等账号 | 登录、授权、健康检查、注销 |
| 消息中心 | 多平台会话和待回复消息 | AI 回复、人工接管、会话跟进 |
| 内容中心 | 素材、剪辑、标题、发布计划 | 内容生产和多平台发布 |
| 获客中心 | 搜索、曝光、评论、私信任务 | 目标筛选和合规触达 |
| 任务中心 | 运行中、等待、失败和历史任务 | 启停、重试、取消、恢复 |
| 审批中心 | 敏感回复和高风险动作 | 人工确认与追溯 |
| 设备中心 | 本机状态、浏览器、微信版本 | 本地执行环境诊断 |
| 日志中心 | 按任务查看步骤和截图 | 脱敏审计与问题排查 |
| 设置 | 更新、存储、模型、隐私和频控 | 客户端和企业策略 |

### 10.5 本地执行器的职责边界

本地 RPA 执行器只负责必须在用户电脑完成的动作：

- 管理专用浏览器配置目录；
- 让用户可见地完成扫码登录；
- 使用 Playwright 操作平台网页；
- 使用 Windows UI Automation 操作桌面微信；
- 必要时使用 OCR 和受控的鼠标键盘模拟；
- 访问用户明确选择的素材文件；
- 保存最少量的加密会话数据；
- 上报步骤、进度、脱敏日志和结果；
- 支持暂停、取消、人工接管和崩溃恢复。

本地执行器不应负责：

- 企业、租户和计费的权威数据；
- LangGraph 的权威运行状态；
- 全局知识库；
- 模型密钥明文管理；
- 跨设备任务编排；
- 绕过验证码、平台安全验证或访问控制。

### 10.6 云端与本地任务协议

建议在现有平台事件协议上增加桌面执行相关事件，而不是让前端直接理解 Playwright 或 Python 内部对象：

```text
device.registered
device.heartbeat
account.login_required
account.login_succeeded
task.assigned
task.started
step.started
step.progress
step.screenshot_available
step.awaiting_human
step.succeeded
step.failed
task.paused
task.cancelled
task.succeeded
task.failed
```

每个任务必须包含：企业、用户、设备、员工、工作流、平台账号、风险等级、幂等键和超时时间。所有事件必须有递增序号，支持断线重连、去重和恢复。

### 10.7 技术实现建议

| 能力 | 推荐实现 |
| --- | --- |
| 桌面壳 | Tauri + Rust，正式开发时锁定明确稳定版本 |
| 业务界面 | 复用现有 React + TypeScript + Ant Design |
| 云端 API | 现有 FastAPI |
| AI 编排 | 现有 LangGraph / Deep Agents 适配层 |
| 素材存储 | 阿里云 OSS，客户端仅获取限定目录、短有效期的 STS 临时凭据 |
| 视频预览 | 阿里云 Timeline 预览组件，通过前端视频预览适配层封装 SDK 加载和错误 |
| 视频渲染 | 第一阶段采用阿里云 IMS/ICE；通过 `VideoRenderProvider` 隔离供应商协议 |
| 本地渲染 | 后续按离线、隐私和成本需求增加 FFmpeg Provider，不作为竞品现状结论 |
| 浏览器自动化 | Playwright，使用 App 专用浏览器目录 |
| Windows 微信 | Windows UI Automation 优先，OCR 作为补充 |
| 图像识别 | OpenCV + OCR，限定到必要区域 |
| 本机通信 | Tauri Command/Channel；Sidecar 使用受认证的本机 IPC |
| 云端下发 | 客户端主动建立出站 WebSocket，避免开放入站端口 |
| 凭据 | Windows Credential Manager/Tauri 安全存储，不进 `localStorage` |
| 本地数据 | 加密 SQLite，按企业和账号隔离 |
| 自动更新 | 签名更新包、灰度、回滚和强制版本策略 |
| 可观测性 | 结构化脱敏日志 + OpenTelemetry 任务关联 |

原竞品使用固定本机 HTTP `9000` 和 WebSocket `8765`。我们的实现不应简单照搬开放端口，而应优先使用 Tauri Channel、命名管道或带随机令牌和严格来源校验的回环 IPC，减少本机其他进程伪造指令的风险。

视频渲染建议定义稳定的供应商抽象：

```text
VideoRenderProvider
├── AliyunIceProvider       # 第一阶段：云端 Timeline 合成
└── LocalFfmpegProvider     # 后续：离线或成本敏感场景
```

业务页面和工作流只依赖 `VideoRenderProvider`，不直接拼装阿里云签名或调用具体 Job API。阿里云 AccessKey 必须保存在服务端，Tauri 客户端只接收最小权限、短有效期的 STS 凭据。任务协议统一描述素材、Timeline、模板、Job、进度、结果、费用和失败原因，使将来切换或并行使用本地 FFmpeg 时不需要重写业务页面。

第一阶段选择阿里云 IMS/ICE 的优势是客户端轻、Mac 和 Windows 结果一致、App 关闭后任务可继续、转场和模板能力成熟；代价是素材需要上传、依赖网络、产生 OSS 和合成费用，并需要明确数据地域、保留期限和删除策略。后续增加本地 FFmpeg，可以覆盖离线、敏感素材和大批量成本场景，但需要自己维护滤镜、字体、转场、编码器兼容和资源调度。

### 10.8 AI 中台底座与客户定制能力

产品定位进一步明确为“一个稳定底座、两个可选行业能力包、多个客户解决方案”：

```text
AI Platform Core（所有客户始终保留）
├── Video Studio（按客户启用）
├── Social Operations（按客户启用）
└── Solution Pack（客户工作流、提示词、品牌和业务配置）
```

AI 中台 Core 包含：

- 企业、工作区、用户、Session、RBAC 和审计；
- 数字员工、LangGraph、Deep Agents 和统一运行时；
- 模型网关、知识库、长期记忆、Skill、Tool、MCP 和沙箱；
- 任务、事件、审批、产物、配额和可观测性；
- Tauri/React 客户端骨架、平台适配、安全凭据、更新和设备基础能力。

视频剪辑属于 `video-studio` 能力包，包含素材库、OSS、Timeline、IMS/ICE、模板、剪辑任务和成片。自动运营属于 `social-operations` 能力包，包含平台账号、Playwright、本地 RPA、微信、朋友圈、私信、内容发布和曝光。

客户交付组合示例：

```text
客户 A = Core + Video Studio + Social Operations + A Solution Pack
客户 B = Core + B Solution Pack
客户 C = Core + Video Studio + C Solution Pack
```

“客户不需要就去掉”不应通过删除代码或维护客户分支实现，而应通过三层机制控制：

1. **部署/安装：** 决定后端模块、Worker、Playwright、OCR 等组件是否随交付安装；
2. **企业授权：** 决定客户是否购买或获准使用能力；
3. **用户权限：** 决定企业内具体用户是否可以查看、执行、审批和管理。

最终可用条件统一为：

```text
deployment_installed && tenant_entitled && user_permitted
```

前端隐藏菜单不能代替安全授权。未授权企业不能通过直接调用接口创建任务、获取 OSS STS、下载 RPA Sidecar 或接收本地执行指令。

首次由单个客户提出、但未来可以复用的能力仍然应实现为通用能力包，不能以客户名称硬编码。只有客户专属 AI 角色、知识绑定、工作流、提示词、内容模板、审批规则、品牌和业务参数进入 Solution Pack。真实凭据、Cookie、联系人、聊天和素材属于运行数据，不进入 Git。

所有客户交付都从同一主干和同一模块注册机制生成。最低测试矩阵覆盖 Core-only、Core+视频、Core+自动运营和正式客户实际组合，确保关闭定制能力后 AI 中台仍然完整可用。

## 11. 功能建设优先级

### 第一阶段：桌面执行闭环

- Tauri 完整客户端框架；
- 设备注册、心跳和自动更新；
- 本地执行器生命周期管理；
- App 专用浏览器和扫码登录；
- 单平台账号管理；
- 抖音或小红书单平台内容发布；
- 任务进度、日志、失败重试和人工接管；
- 凭据加密和安装包签名。

目标是先证明“用户只在一个 App 内完成登录、配置、执行、查看结果”的完整体验。

### 第二阶段：多平台发布和 AI 客服

- 抖音、小红书、快手、视频号聚合发布；
- 阿里云 OSS 素材库和受限 STS 上传；
- 阿里云 IMS/ICE Timeline 预览、模板剪辑和异步成片；
- 视频渲染 Provider、批量任务、进度、费用和失败重试；
- 多平台发布记录；
- 抖音官方能力优先的 AI 客服；
- 会话中心、知识库回复和审批；
- 频控、熔断和账号健康度。

### 第三阶段：微信本地 RPA

- PC 微信环境诊断；
- UI Automation 控制；
- OCR 未读与消息识别；
- AI 回复建议和人工确认；
- 在风险验证充分后逐步开放自动发送；
- 好友申请、群发和朋友圈分开灰度。

微信桌面 UI 变化快、隐私风险高，应该在浏览器发布链路稳定后再做，不建议第一阶段同时铺开。

### 第四阶段：获客工作流

- 自动、定向、链接和账号搜索任务；
- 目标用户筛选；
- 评论和私信策略；
- 可视化工作流；
- 企业级审批、配额、审计和合规策略；
- 任务效果和转化分析。

获客自动化是平台风控最高的部分，只能在账号保护、审批、审计和远程熔断全部具备后开放。

## 12. 与当前 agent-platform 的结合点

当前项目已有企业、工作区、数字员工、运行任务、知识、Skill、Tool、审批、事件和审计等平台基础。无需重新建设一套独立 RPA 管理后端，建议增加以下边界：

```text
backend/src/agent_platform/
├── devices/              # 桌面设备注册、心跳和版本
├── platform_accounts/    # 平台账号元数据和授权状态
├── rpa_tasks/            # 本地执行任务、租约、重试和结果
├── automation_policies/  # 频控、审批、风控和熔断
└── runtimes/             # 通过公开协议调用本地执行能力

frontend/src/
├── features/devices/
├── features/platform-accounts/
├── features/rpa-tasks/
├── features/conversations/
├── features/content-publishing/
└── platform/             # Web/Tauri 统一 PlatformAdapter

frontend/src-tauri/
├── commands/             # 原生能力入口
├── sidecar/              # 本地执行器生命周期与 IPC
├── credentials/          # 系统安全凭据
└── updater/              # 签名更新和回滚
```

这只是建议边界，不代表当前仓库已经存在这些目录。正式实现前需要同步更新 `docs/project-structure.md`、`docs/backend-architecture.md` 和 `docs/frontend-architecture.md`，把本地 RPA Sidecar、设备协议和安全边界纳入架构基线。

## 13. 不能直接照抄竞品的地方

1. 不把真实运行日志打进安装包；
2. 不发布未签名的安装程序和自动更新包；
3. 不默认开放固定本机 HTTP/WebSocket 端口；
4. 不在普通日志中记录完整聊天、Cookie、账号和联系人；
5. 不用 stealth 当作平台合规或账号安全保障；
6. 不把验证码、安全校验和封控当作要自动绕过的障碍；
7. 不把 UI 自动化当成唯一方案，平台有官方 API 时优先使用 API；
8. 不把 AI 生成的高风险内容未经校验直接发送；
9. 不让云端能够在用户不知情时随意控制鼠标键盘；
10. 不把云端 Agent 后端完整塞进客户端，本地只保留必要执行能力；
11. 不要求用户在 App 与 Web 之间来回切换完成同一个流程；
12. 不一次性支持所有平台，先把一个平台的登录、执行、恢复、审计做完整。
13. 不让业务页面直接依赖阿里云具体接口，必须通过视频渲染 Provider 隔离供应商；
14. 不把长期 AccessKey 放进客户端，素材上传只使用最小权限、短有效期的 STS。

## 14. 购买账号后的动态验收计划

### 14.1 验收环境

当前开发电脑是 macOS，无法原生运行该 Windows EXE，也不能验证 Windows UI Automation 和 PC 微信行为。推荐准备一台专用 Windows 测试机，要求如下：

- 不使用保存了个人主账号、公司生产凭据的日常办公电脑；
- 使用测试微信、测试抖音号和其他测试平台账号；
- 记录 Windows 版本、显示缩放、微信版本和浏览器版本；
- 在安装前记录进程、服务、计划任务、开放端口和关键目录基线；
- 安装后只授予完成测试所需的权限；
- 允许随时断网、结束进程和恢复快照。

虚拟机可以用于初步界面观察和网络分析，但不应在销售未确认解绑规则前用购买账号首次激活，因为虚拟机可能被记为正式绑定设备，而且桌面微信、显卡、DPI 和窗口行为与真实 Windows 电脑存在差异。

Mac 仍然可以继续开发 Tauri 的 React 界面、云端 API、任务协议和大部分跨平台逻辑。Windows 专属的 UI Automation、安装包、代码签名、自动更新、微信 RPA 和真实平台登录，必须在 Windows 环境持续开发和验收，不能只靠 Mac 上的单元测试判定完成。

### 14.2 激活前向销售确认

1. 一个账号包含几个设备席位；
2. 首次登录是否立即绑定设备；
3. 设备绑定依据和隐私说明；
4. 是否有自助解绑入口；
5. 重装系统和更换硬件如何恢复；
6. 一年内允许换机或解绑多少次；
7. 账号能否在多台设备同时在线；
8. 试用、退款和授权到期后的数据处理方式；
9. 客户端会把哪些聊天、Cookie、截图和素材上传云端；
10. 是否允许在自有测试环境中做进程、文件、端口和网络流量检查。

### 14.3 动态验收顺序

| 顺序 | 验收项 | 需要记录的结果 |
| --- | --- | --- |
| 1 | 安装与启动 | 安装目录、签名提示、进程、服务、开机启动、更新机制 |

### 14.4 设备绑定专项测试

设备绑定测试只能走厂商提供的正常流程，不尝试伪造机器信息或绕过授权：

1. 在预定的专用 Windows 机首次登录，截取绑定提示和设备信息；
2. 在产品内查找设备管理、退出和解绑入口；
3. 退出账号并重新登录，确认本机授权是否保留；
4. 按厂商说明完成一次正式解绑；
5. 经销售确认后在第二台测试机登录，验证席位迁移；
6. 再回到第一台机器，确认旧设备授权是否失效；
7. 记录异常情况下的客服恢复流程和耗时。

## 15. 最终判断

探能 AI 员工不是概念演示，而是一套实际运行过的桌面运营自动化产品。它的核心竞争力并非某一种单独技术，而是把以下能力放进同一个 Windows 客户端：

- AI 对话和内容生成；
- 微信桌面 RPA；
- 多平台浏览器自动化；
- 视频素材与批量发布；
- 阿里云 OSS、Timeline Web SDK 和 IMS/ICE 云剪辑；
- 私信客服与持续跟进；
- 自动曝光和获客；
- 工作流和任务管理。

它也暴露出明显问题：安装包和关键程序未签名、发布包夹带真实运行日志、浏览器自动化容易受页面改版影响、社交平台自动化存在封号风险、客户端能够接触大量敏感数据。

我们可以做同类产品，而且产品形态应当就是一个完整桌面 App。正确做法不是把所有功能强行放到纯网页，也不是让用户在 App 和网页之间切换，而是：

> 用 Tauri + React 构建统一桌面界面，用阿里云 IMS/ICE 或可替换 Provider 完成视频渲染，用受控本地执行器完成浏览器和 Windows RPA，用现有 agent-platform 云端负责 AI、工作流、知识、权限、审批和审计。

这样既保留桌面 RPA 必需的本机能力，也能复用当前平台已经建立的后端和前端基础，并为后续企业 Web 管理端保留同源复用能力。
